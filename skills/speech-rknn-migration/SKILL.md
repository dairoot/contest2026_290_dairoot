# 语音模型 ASR、VAD 迁移到 RKNN NPU

将可计算的网络部分迁移到 NPU，同时保留音频前端和应用状态语义。先核对模型图、状态和输入输出，再选择迁移范围；转换成功和运行正确是两个验收阶段。

## 项目边界与入口

本项目 `linux-apps/asr-server/` 已实现 **SenseVoiceSmall ASR 的 RKNN 后端**，另有 ERes2NetV2 声纹迁移经验。**FSMN-VAD 当前没有 RKNN 导出脚本或后端**：`vad.py` 通过 FunASR 运行，在 RK3576 板上走 CPU；开发机可由 `utils/_device.py` 选择 CUDA/MPS。

用户只要恢复项目时保留现有 VAD；用户明确要求 VAD 上 NPU 时，按下面的有状态迁移流程实施，不把“当前 CPU 实现”解释为“VAD 不能上 NPU”，也不把评估方案描述成已完成迁移。

定位项目根为 `CONTEST_ROOT`。独立安装 Skill 仍需项目源码或用户的目标语音工程，不假设 Skill 所在目录就是源码根。

## 推荐转换环境：Ubuntu x86_64

**默认在 Ubuntu x86_64 上建立独立 Toolkit2 环境并完成 RKNN 转换，再将 `.rknn` 部署到开发板。** 环境准备、ASR/声纹导出转换、模型传输和运行库检查统一在 [ASR/声纹执行参考](references/asr-project-workflow.md) 中维护。

- **导出 ONNX**：可在满足 PyTorch 依赖的 macOS/Linux 上执行，也可统一放在 Ubuntu 转换机。
- **转换 RKNN**：推荐 Ubuntu x86_64；本项目使用的 Toolkit2 包在 Linux 上运行，不安排在 macOS 原生环境转换。ASR 转换需 8 GB 以上内存并留余量，避免在本项目 3.8 GB 的 RK3576 板上转换 ASR。
- **VAD 后续迁移**：同样优先使用 Ubuntu 转换环境，但其导出、资源需求和数值结果仍需单独验证；本项目已验证的 RKNN 模型是 ASR 和声纹。

## 迁移前先确认

读取模型/权重版本、目标 SoC、转换机架构和内存、Toolkit2/Lite2/runtime/驱动版本、音频格式、窗口大小和性能目标。不要把历史 RK3576 的核数、时延和 SDK 约束套到其他芯片。

把每个模型列成“原始输入 → CPU 前端 → 网络张量 → 网络输出 → CPU 后处理/状态”。记录 shape、dtype、layout、长度语义和缓存生命周期；缓存和长度输入不能为了通过转换而随意删掉。

当前分支支持方式、安装约束有时效性；新环境查对应版本官方资料。本项目参考版本和命令在 [ASR 执行参考](references/asr-project-workflow.md)。

## ASR 迁移路径

1. **固定参考输入。** 保存同一组 16 kHz 单声道 Float32 音频，包含短句、接近窗口长度、跨窗长句、静音、轻声与噪声。先获得 CPU 参考文本和耗时。项目公共前端位于 `asr_model/_sense_voice_common.py`，包含 fbank/LFR/CMVN 与 CTC 解码，迁移后继续共用。
2. **导出定长 fp32 ONNX。** 本项目从未量化的 SenseVoiceSmall 权重出发，以 batch=1、默认 5 s 为基线；不把 CPU int8 ONNX 直接当成本流程输入。当前固定中文/withitn 的标量可固化；用户需要切换语言或文本规范时，重新设计输入或模型变体，不能偷偷固定中文。
3. **先校验 ONNX。** 比较原模型与定长 ONNX 的输出/解码，检查短句补零及超窗处理，再用 Toolkit2 转换。定长是本项目导出器/运行器契约，不是关于所有 RKNN 版本的动态 shape 能力断言。
4. **先 fp16，再决定量化。** 保留不量化基线，int8 需要匹配模型输入张量的校准集和独立精度对照。本项目网络输入是已归一化的语音特征，不能套用图像 `/255` 或给校准器原始 JPEG/WAV。
5. **接入运行器。** 默认 ASR 短句补零到 5 s；超窗长句按当前 `_infer_utterance` 逻辑切分，尾窗向前对齐并按输出帧去除重叠。核对 prompt 帧和 LFR 帧移，跨窗处用真实录音验证漏字/重复字。换模型不能照抄该解码规则。
6. **测整个服务。** 先对同一模型的 fp32 ONNX 与 RKNN 比精度，再与现有 CPU int8 服务比耗时/资源。分别报告前端、推理、解码、排队和“说完到结果”的时延；窗口越大不一定越好。

## VAD 有状态迁移路径

涉及 VAD 时读取 [FSMN-VAD 迁移与验收](references/vad-stateful-migration.md)。按四个层次处理：

1. **抽取网络边界。** 音频前端缓存、FSMN 网络缓存、端点判决状态、会话时间轴分开。识别目标版本实际的网络缓存输入/输出，不把 Python `vad_cache` 字典整体塞进 ONNX。
2. **先验证 ONNX 流式等价。** 固定每次特征帧数，保留固定 shape 的缓存张量；第一个 chunk 初始化，后续 chunk 回传新缓存。前端与端点状态继续在 CPU，保留有效长度与末包处理。
3. **再转 RKNN 和接入。** 建立显式的缓存映射，逐块对拍 logits、缓存和端点输出；通过后才接入现有 `VadWorker` 接口。导出失败时先定位具体算子/shape，不能把逐块重置缓存作为修复。
4. **验收收益。** 测每个 chunk 的前端、数据搬运、网络、后处理总耗时和并发排队。只有网络成功运行而端点错位、句尾不闭合或会话状态串扰，都不能算迁移完成。

如果当前环境无法跑目标模型或真机，交付已验证到的阶段、可复现失败和剩余验证步骤。需要保留 CPU 路径时说明具体原因与测量依据。

## 常见误判

| 现象 | 处理 |
| --- | --- |
| 转换机缺内存 | 优先换到足够内存的 Ubuntu x86_64 转换机；不要把 3.8 GB 开发板当成 ASR 编译服务器 |
| `load_rknn/init_runtime` 失败 | 核对 target、模型格式、实际加载的 `librknnrt.so`、用户态与驱动版本 |
| 文本几乎为空或输出异常 | 查前端、输入 shape、dtype、窗口配置、模型/词表版本；勿先改 CTC 阈值 |
| VAD 整段离线正常、流式错误 | 查缓存回传、跨块前端拼接、有效长度、状态 reset 和全局时间轴 |
| NPU 推理快，交互仍慢 | 拆开端点等待、前端、ASR 队列、NPU 争用与声纹开销 |
| 服务能启动却没用 NPU | 核对实际后端与加载日志；缺模型/包可能触发 CPU 回退，配置值不是运行证据 |

## 交付与验收

交付模型来源/版本、转换脚本或配置、输入输出契约、模型哈希、部署方式和回退方式。ASR 报告参考集 CER/WER 或逐条差异；VAD 报告起止边界、漏检/误检、端点延迟、reset/多会话正确性；同时给出冷启动、预热后延迟与峰值内存。

区分“本项目已实现的 ASR”“本次实际验证的 VAD 阶段”。禁止用声纹的 RKNN 成果充当 VAD 成果；没有真机结果时不承诺加速倍数。
